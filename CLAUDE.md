## What's Being Built

ORCA: an agentic marine-intelligence assistant (Phase 1 of a larger platform). A LangGraph pipeline of specialist agents (planner → geospatial → weather → risk → ocean_analytics → reporting) answers three query types end-to-end — "is it safe to go out", "where's the nearest fishing zone", "any cyclone/lightning alerts" — with real correlation logic and a visible reasoning trace, backed by free/no-cost external data sources only.

## Architecture (once implemented, per the plan)

**Monorepo layout:** `backend/` (Python/FastAPI/LangGraph) and `frontend/` (Next.js/TypeScript), each with their own dependency and test tooling.

**Backend pipeline (`backend/app/graph.py`):** a fixed LangGraph sequence, not dynamic fan-out:
`planner → geospatial → weather → risk → ocean_analytics → reporting → END`, with one conditional decision point after the planner (still a single `add_conditional_edges` call, statically defined — not runtime graph construction) that now has three destinations: `geospatial` for a single-location query, `route` for a two-location route query (`route → reporting`, bypassing the single-location chain entirely — see Post-MVP additions), or straight to `reporting` if the planner couldn't resolve a location, which asks the user for one. Every node appends a `TraceEntry` to `state["trace"]`; this trace is streamed to the frontend and *is* the "make agentic reasoning visible" requirement, not optional logging.

**Connector contract (`backend/app/connectors/`):** every external data source (weather, SST, chlorophyll, alerts, geocoding) is one module implementing the same shape — return a `ConnectorResult{data, source, fetched_at, is_cached}` via the shared `fetch_with_fallback()` helper in `connectors/base.py`, which retries a live fetch once, then falls back to a committed snapshot file in `backend/data/snapshots/`. **A connector must never fabricate data** — no live source, no cache miss is architecturally impossible because every connector ships its own snapshot. New data sources plug in by adding one module with this same interface; agents and the graph never change.

**Agents (`backend/app/agents/`)** are thin: each wraps one or more connectors, adds real domain logic (threshold checks, correlation scoring), and returns `(output_dict, TraceEntry)`. The only two agents that call an LLM are `planner.py` (structured-output intent/plan extraction) and `reporting_agent.py` (final NL synthesis) — both via `app/llm.py`.

**Post-MVP additions (2026-09-15, still Phase 1 scope):**
- `ocean_analytics_agent.py` also fetches a real 7-day SST time series (`connectors/ocean_analytics.get_sst_trend`, ERDDAP time-range query, own snapshot) and computes `sst_trend_direction` ("warming"/"cooling"/"stable") via a simple threshold on first-vs-last delta — real historical data, not fabricated, giving the reporting agent something to reason about for "why has it changed" style questions instead of only a single point-in-time snapshot.
- `geospatial_agent.py` now emits a deterministic `geofence_warning` string when `within_warning_zone` is true — code-guaranteed, not left to the reporting LLM's discretion to notice. `reporting_agent.py`'s prompt requires surfacing it prominently even when the user's question wasn't primarily about boundaries.
- `frontend/components/SstTrendChart.tsx` renders `sst_trend_celsius` as an inline SVG sparkline inside `ReasoningTrace`, replacing the raw-JSON-only view for that field.
- **Cyclone alerts are now live**, closing a Phase 2 item early: `connectors/alerts.get_cyclone_alerts` queries GDACS (`gdacs.org/gdacsapi`, free, no key), filters to currently-active `TC` events within 500km (haversine) of the query location, and falls back to a cached (honestly empty) snapshot on failure. `get_lightning_alerts` still has **no live source** — Blitzortung, the usual free community network, requires an authenticated websocket rather than a simple REST endpoint; it stays on a cached, always-empty snapshot. `risk_agent.py` now calls both connectors and combines them (`max()` for `fetched_at`, `or()` for `is_cached`, same pattern as `ocean_analytics_agent`).
- **Geofencing is now live too**, closing another Phase 2 item: `connectors/geospatial.get_nearby_boundary` replaces the old static single-example-polygon (`shapely`, `mpa_boundaries.geojson` — both removed) with a real Overpass API query (`overpass-api.de`, free, no key, requires a descriptive `User-Agent` or it 406s) against OpenStreetMap's `boundary=protected_area` tags, picking the nearest **named** feature (unnamed sub-geometries are skipped — not useful to cite to a user) within 100km via haversine distance to each feature's center point (an approximation: center-to-point, not true polygon-edge distance, since Overpass's `out center` doesn't give full boundary geometry cheaply). Falls back to a real captured snapshot (`nearby_boundary.json`, a genuine nearby sanctuary near Kochi, not fabricated placeholder data) on failure. `geospatial_agent.py`'s `fetched_at`/`is_cached` now correctly combine both the geocode and boundary connector results (`max()`/`or()`), where before it silently ignored the boundary check's own staleness.
- **Persistent per-session history**, closing a Phase 2 item (with a scope limit — see below): `backend/app/db.py` is a small SQLite module (not the spec's literal "Postgres" — zero-config, file-based, no server process, gitignored at `backend/data/orca.db`) with `init_db()`, `get_history(session_id)`, `append_message(session_id, role, content)`. `POST /chat` no longer trusts client-sent history — it loads history from the DB by `session_id` and persists both the user's message and the final answer after each turn. A new `GET /sessions/{session_id}/history` endpoint lets the frontend restore history on page load. `ChatRequest.history` is removed entirely. **Scope limit: this is persistent history, not real multi-user accounts** — a "session" is just whatever `session_id` the client holds (now cached in `localStorage`, not regenerated every page load); there is no login/auth, and anyone who knows a session_id can read its history. Real accounts stay explicitly out of scope.
- **Proactive/push alerting**, closing another Phase 2 item — scoped explicitly to **in-app delivery while the browser tab is open**, no service worker/push subscription/email/SMS (a deliberate design decision, not a shortcut discovered later). `backend/app/alerting.py`: every 5 minutes (`DEFAULT_CHECK_INTERVAL_SECONDS`), every session with a known last-resolved location (`db.set_last_location`, captured automatically from the geospatial trace entry after each `/chat` turn) is re-checked against live `weather_agent`/`risk_agent` — the same agents the main pipeline uses, no new hazard logic. An alert publishes only on a **transition into "unsafe"** (`db.get_last_verdict`/`db.set_last_verdict` track state to avoid re-alerting every poll while still unsafe, or alerting on recovery to safe). Delivery is a long-lived SSE endpoint, `GET /sessions/{session_id}/alerts/stream`, backed by an in-memory `dict[session_id, list[asyncio.Queue]]` subscriber registry in `alerting.py` (`subscribe`/`unsubscribe`/`publish`) — a 15s keep-alive `: ping` comment prevents proxy/load-balancer idle timeouts. The background poller starts via a FastAPI `lifespan` context manager (`asyncio.create_task(alerting.run_periodic_checks())`). Frontend: `chatClient.subscribeToAlerts()` wraps the native `EventSource` API (this endpoint is GET-only, unlike `/chat`, so `EventSource` works natively — no manual SSE parsing needed here) and `page.tsx` shows a dismissible banner on the incoming alert. **Real limitation, not hidden:** if no tab is open for a session when a hazard develops, the alert is silently missed — there is no way to reach the user outside an open connection in this design.
- **Route Safety Agent** (`backend/app/agents/route_agent.py`), closing the last originally-deferred Phase 2 item — with an explicit, user-confirmed scope limit: **this is a waypoint hazard SCAN, not a navigational path planner.** No land-avoidance, no shipping-lane data, no bathymetry; waypoints are simple linear interpolation between two geocoded endpoints (a real simplification beyond short coastal hops, honestly documented). `run_route_agent(start_lat, start_lon, end_lat, end_lon)` samples `WAYPOINT_COUNT` (5) waypoints, runs the *existing* `weather_agent`/`risk_agent` at each (no new hazard logic, same pattern as `alerting.py`), and for any `"unsafe"` waypoint computes one perpendicular-offset detour point (`DETOUR_OFFSET_KM` = 20km) and re-checks it — reporting the detour only if it comes back safe, `None` otherwise (no iterative search). The planner (`planner.py`) gained `start_place_name`/`end_place_name` fields, populated only for genuine route queries (e.g. "safest route from Kochi to Alappuzha"); `graph.py`'s conditional routing sends these straight to a new `route` node (`route → reporting`, bypassing `geospatial`/`weather`/`risk`/`ocean_analytics` entirely) which geocodes both endpoints and calls the route agent. `MapView.tsx` renders the route as colored `Polyline` segments (red across any hazardous waypoint pair, blue otherwise) with a `CircleMarker` per waypoint (red/green) and a popup showing that waypoint's verdict and reasons.

**LLM constraint:** a two-provider fallback chain implemented in `app/llm.py`'s `LLMClient` — no paid-per-token API of any kind for either provider. Priority provider is **Omniroute**, a local OpenAI-compatible proxy at `http://127.0.0.1:20128/v1` (`OMNIROUTE_API_KEY`); it reliably enforces JSON-schema-constrained structured output (`response_format: json_schema`), which the planner depends on. Fallback provider is **Ollama Cloud** (`https://ollama.com/api`, `OLLAMA_API_KEY`, model `gemma4:31b`) for when Omniroute is unreachable — Ollama Cloud does *not* reliably honor schema constraints, so its path does manual JSON extraction from the response text with one retry before giving up. `LLMClient` exposes `generate_text(system_prompt, user_message)` and `generate_structured(system_prompt, user_message, schema)`; agents never talk to a provider SDK directly. Both agents that call an LLM (`planner.py`, `reporting_agent.py`) go through this client.

*Portability caveat:* Omniroute only exists on the machine it was configured on (`127.0.0.1`) — the app will only reach it when run from that same machine with the proxy already running. Anywhere else (a fresh clone, a deploy target, a different developer's machine), only the Ollama Cloud fallback path is reachable. (History: the original Phase 1 implementation used Google Gemini's free tier, which broke when `gemini-2.5-flash` was deprecated for new API keys and its successors proved unreliable/rate-limited on a fresh key; switched to the current two-provider chain on 2026-09-15.)

**Other deliberate deviations from a naive reading of the spec** (see the plan's "Global Constraints" section for the full list): SST/chlorophyll come from NOAA ERDDAP (`jplMURSST41`, `erdMH1chla1day` — free, no registration) rather than Copernicus/NASA; the map uses Leaflet + OpenStreetMap tiles (no API key) rather than Mapbox. (Note: "no database in Phase 1, frontend resends history" was the *original* Phase 1 design; a SQLite-backed persistent history layer was added post-MVP on 2026-09-15 — see above.)

**Frontend (`frontend/`):** the backend's `/chat` endpoint streams Server-Sent Events (`event: trace`, `event: answer`) over a POST request — the native `EventSource` API doesn't support POST, so the client (`frontend/lib/chatClient.ts`) hand-parses the stream via `fetch` + `ReadableStream`. `MapView` (Leaflet) must be loaded via `next/dynamic` with `ssr: false` since Leaflet touches `window`.

## Commands (once Phase 1 is implemented per the plan)

Backend (from `backend/`):
- `pytest -v` — run all tests; `pytest tests/test_<name>.py -v` for a single file
- `uvicorn app.main:app --reload --port 8000` — run the dev server (requires `OMNIROUTE_API_KEY` and/or `OLLAMA_API_KEY` env vars; Omniroute only works when its local proxy is running on the same machine)

Frontend (from `frontend/`):
- `npm test` — run Vitest unit tests
- `npx tsc --noEmit` — type-check
- `npm run dev` — run the dev server (expects backend at `http://localhost:8000`, override via `NEXT_PUBLIC_BACKEND_URL`)
