## What ORCA Is

An agentic marine-intelligence assistant for fishermen, coastal stakeholders, and marine researchers (built for Smart India Hackathon problem statement SIH26176). A LangGraph pipeline of specialist agents answers real queries end-to-end — "is it safe to go out", "where's the nearest fishing zone", "any cyclone/lightning alerts", "safest route from A to B", "why has it changed", "what's the tide right now" — with real correlation logic, evidence-grounded verification, and a visible reasoning trace, backed only by free/no-cost external data sources.

## Architecture

**Monorepo layout:** `backend/` (Python/FastAPI/LangGraph) and `frontend/` (Next.js/TypeScript), each with their own dependency and test tooling.

**Backend pipeline (`backend/app/graph.py`):** a fixed LangGraph sequence, not dynamic fan-out:
`planner → geospatial → weather → risk → ocean_analytics → reporting → END`, with one conditional decision point after the planner (still a single `add_conditional_edges` call, statically defined — not runtime graph construction) that has three destinations: `geospatial` for a single-location query, `route` for a two-location route query (`route → reporting`, bypassing the single-location chain entirely), or straight to `reporting` if the planner couldn't resolve a location, which asks the user for one. Every node appends a `TraceEntry` to `state["trace"]`; this trace is streamed to the frontend and *is* the "make agentic reasoning visible" requirement, not optional logging.

`GraphState` (`graph.py`) carries more than just per-agent results: `canonical_location` accumulates resolved-location metadata across nodes (geocode result, then `grid_distance_km` once weather resolves a forecast grid point), and `evidence` accumulates every `MarineParameter` (see below) emitted by `weather_node`/`ocean_analytics_node` as the pipeline runs — not just the final answer's headline numbers. `reporting_node` closes the loop: before synthesizing the final answer it (1) runs `verification_agent.audit_marine_evidence()` over the full accumulated `evidence` + trace `sources` to produce a `VerificationResult` (is this answer actually grounded in real data, or thin/stale?), and (2) — only for what-if-shaped queries (different departure time, or "what if I move N km <direction>") — runs `what_if_agent.run_what_if_agent()` to produce a `WhatIfComparison` between the original and alternative scenario. Both are returned alongside `final_answer` in the `/chat` SSE `answer` event and rendered by the frontend (see below), not just logged.

**Connector contract (`backend/app/connectors/`):** every external data source (weather, SST/chlorophyll, alerts, geocoding, geofencing, PFZ advisory, IMD warnings, ISRO/MOSDAC satellite data) is one module implementing the same shape — return a `ConnectorResult{data, source, fetched_at, is_cached}` via the shared `fetch_with_fallback()` helper in `connectors/base.py`, which retries a live fetch once, then falls back to a committed snapshot file in `backend/data/snapshots/`. **A connector must never fabricate data** — no live source, no cache miss is architecturally impossible because every connector ships its own snapshot. New data sources plug in by adding one module with this same interface; agents and the graph never change.

**A real violation of that contract shipped and was fixed — read this before touching any connector.** `connectors/incois.py`'s `_live_fetch_incois()` used to make one real HTTP call to INCOIS's public `OSF_CoastalForecast` GeoServer WFS layer to confirm a coastal sector exists, then — on any successful response — returned **hardcoded** wave height (2.3m), wind speed (28.5 km/h), SST (28.4°C), etc., labeled `data_status: "LIVE"`, `is_cached: False`, `source: "INCOIS"`. This was verified live against the real WFS endpoint: it returns sector boundary metadata only (`SECTORNAME`, `SEC_ID`, geometry) — no wave/wind/swell/current/SST attributes exist in that layer at all, so there was no honest way to serve "live" numeric values from it. Every query for months returned bit-identical fabricated numbers dressed up as live observations. Fixed by making `_live_fetch_incois()` always raise (after a real, still-useful in-coverage check) so `fetch_with_fallback` uses the disclosed cached snapshot instead — same honest pattern IMD/MOSDAC already used. Regression coverage: `tests/test_connector_incois.py::test_live_fetch_incois_still_never_fabricates_even_if_wfs_responds` mocks a *successful* WFS response and asserts the function still raises, specifically so a future re-introduction of a "parse the WFS response into current_conditions" shortcut gets caught. (A real live path exists in principle — INCOIS's THREDDS NCSS interface, documented in `docs/data-sources.md`, does carry real numeric values — but isn't implemented; if you build it, verify against the *actual* endpoint before trusting any assumed response shape, the way this incident should have been caught the first time.)

**Agents (`backend/app/agents/`)** are thin: each wraps one or more connectors, adds real domain logic (threshold checks, correlation scoring), and returns `(output_dict, TraceEntry)`. The only two agents that call an LLM are `planner.py` (structured-output intent/plan extraction) and `reporting_agent.py` (final NL synthesis) — both via `app/llm.py`. Three agents don't sit on the main pipeline as graph nodes but are called from within `reporting_node`/`risk_agent`: `risk_engine.py` (a deterministic, weighted `calculate_risk()` scoring function — thresholds documented in-file as prototype decision-policy heuristics, *not* statutory/official INCOIS/IMD standards), `verification_agent.py` (`audit_marine_evidence()`), and `what_if_agent.py` (`run_what_if_agent()`).

**`risk_agent.py` produces two parallel risk representations, not one — this is easy to miss:** a legacy binary `verdict`/`reasons` (simple threshold check via `_assess()`, unchanged since Phase 1) that `route_agent.py` and `alerting.py` still key off of for hazard-scan/unsafe-transition logic, *and* a richer `risk_score`/`risk_level`/`factors`/`recommendation`/`confidence` from `risk_engine.calculate_risk()` that feeds `RecommendationHero` on the frontend. Both are computed from the same inputs every call; don't assume they're redundant or that one supersedes the other — they serve different consumers.

**Feature history and deliberate deviations from the original spec** (roughly chronological; each closes an item the spec explicitly deferred to "Phase 2," unless noted):
- `ocean_analytics_agent.py` fetches a real 7-day SST time series (`connectors/ocean_analytics.get_sst_trend`, ERDDAP time-range query, own snapshot) and computes `sst_trend_direction` ("warming"/"cooling"/"stable") via a simple threshold on first-vs-last delta — real historical data, not fabricated, giving the reporting agent something to reason about for "why has it changed" style questions instead of only a single point-in-time snapshot.
- `geospatial_agent.py` emits a deterministic `geofence_warning` string when `within_warning_zone` is true — code-guaranteed, not left to the reporting LLM's discretion to notice. `reporting_agent.py`'s prompt requires surfacing it prominently even when the user's question wasn't primarily about boundaries.
- `frontend/components/SstTrendChart.tsx` renders `sst_trend_celsius` as an inline SVG sparkline inside `ReasoningTrace`, replacing a raw-JSON-only view for that field.
- **Cyclone alerts are live:** `connectors/alerts.get_cyclone_alerts` queries GDACS (`gdacs.org/gdacsapi`, free, no key), filters to currently-active `TC` events within 500km (haversine) of the query location, and falls back to a cached (honestly empty) snapshot on failure. `risk_agent.py` calls both cyclone and lightning connectors and combines them (`max()` for `fetched_at`, `or()` for `is_cached`, same pattern as `ocean_analytics_agent`).
- **Lightning alerts are live** (this corrects an earlier wrong conclusion that no free feed existed): the raw Blitzortung.org websocket obfuscates its payload and was written off as impractical — but `blitzortung.ha.sed.pl:1883` is a real, free, **unauthenticated MQTT broker** (run by the maintainer of the Home Assistant Blitzortung integration, see `github.com/mrk-its/homeassistant-blitzortung`) that already republishes the decoded real-time strike feed as plain JSON — no reverse-engineering needed. `connectors/alerts.py`: `_geohash_encode()` (standard algorithm, verified against the canonical Wikipedia example) computes geohash tile prefixes covering a point plus a radius (`_tile_prefixes`, 8 compass-offset samples — an approximation of true bbox-overlap tile coverage); `_listen_for_strikes()` is a blocking `paho-mqtt` connect-subscribe-collect-for-N-seconds call (`LIGHTNING_LISTEN_SECONDS = 5`), wrapped in `asyncio.to_thread` so it doesn't block the event loop; strikes are filtered to real haversine distance. **This is a real-time SAMPLE, not a historical query or continuous monitor** — a strike just outside the listen window is genuinely missed, and an empty result honestly means "none observed in this window," not "none exist." `get_lightning_alerts` uses the same `fetch_with_fallback` pattern as every other connector, falling back to the (still-empty) cached snapshot only if the broker connection itself fails. **Test isolation note:** `_listen_for_strikes` is MQTT, not HTTP, so `respx` can't intercept it — e2e tests must monkeypatch it directly (see `test_e2e_query_types.py`'s `_mock_all_connectors`) or they'll spend 5+ real seconds per test hitting the live broker. `risk_agent.run_risk_agent()` now calls cyclone and lightning concurrently (`asyncio.gather`) rather than sequentially, since lightning alone imposes that 5s floor and the two calls are independent.
- **Geofencing is live:** `connectors/geospatial.get_nearby_boundary` replaces the old static single-example-polygon (`shapely`, `mpa_boundaries.geojson` — both removed) with a real Overpass API query (`overpass-api.de`, free, no key, requires a descriptive `User-Agent` or it 406s) against OpenStreetMap's `boundary=protected_area` tags, picking the nearest **named** feature (unnamed sub-geometries are skipped — not useful to cite to a user) within 100km via haversine distance to each feature's center point (an approximation: center-to-point, not true polygon-edge distance, since Overpass's `out center` doesn't give full boundary geometry cheaply). Falls back to a real captured snapshot (`nearby_boundary.json`, a genuine nearby sanctuary near Kochi, not fabricated placeholder data) on failure. `geospatial_agent.py`'s `fetched_at`/`is_cached` correctly combine both the geocode and boundary connector results (`max()`/`or()`).
- **Tide data:** `connectors/weather.py` extends the *existing* Open-Meteo Marine call (same host, no new dependency) to also request `sea_level_height_msl` over the next ~48h. `_parse_tide_series()`/`_next_tide_extrema()` derive `tide_height_m` (now) and `next_high_tide`/`next_low_tide` (`{time, height_m}`, first local max/min after the series start) from the hourly series. Surfaced in `weather_agent.py`'s output plus one `MarineParameter` (source `open-meteo-marine`, `data_status: "FORECAST"`, confidence 0.75 — deliberately lower than INCOIS's 0.92, since this is model-derived at ~8km resolution and referenced to mean sea level, not an official INCOIS tide table or chart datum). `ReasoningTrace.tsx` renders it inline on the `weather` trace entry, same pattern as the geofence-warning callout.
- **Route Safety Agent** (`backend/app/agents/route_agent.py`) — with an explicit, user-confirmed scope limit: **this is a waypoint hazard SCAN, not a navigational path planner.** No bathymetry. `run_route_agent(start_lat, start_lon, end_lat, end_lon)` runs the *existing* `weather_agent`/`risk_agent` at each waypoint (no new hazard logic, same pattern as `alerting.py`). For any `"unsafe"` waypoint, `_find_safe_detour()` checks up to `len(DETOUR_DISTANCES_KM) * len(DETOUR_SIDE_OFFSETS)` candidates (currently 2 distances × 2 sides = 4) **concurrently** (`asyncio.gather`, so searching more candidates doesn't add latency vs. checking just one) and returns the nearest safe one. When found, the route is actually rerouted through it — not just noted as a side comment — the returned waypoint gets `rerouted: true` and `original: {lat, lon, reasons}` (the hazardous point's own data, preserved for transparency), so the plotted path genuinely bends around the hazard. `overall_verdict` has three states: `"safe"` (no rerouting needed), `"safe_with_detours"` (all waypoints resolved safe, but rerouting was needed for at least one), `"hazardous_segments"` (at least one waypoint has no safe candidate even after the wider search — `detour: None`, `rerouted` key absent). `planner.py` has `start_place_name`/`end_place_name` fields, populated only for genuine route queries; `graph.py`'s conditional routing sends these to the `route` node (`route → reporting`, bypassing `geospatial`/`weather`/`risk`/`ocean_analytics` entirely). `MapView.tsx` renders the route as colored `Polyline` segments (red across any hazardous waypoint pair, green otherwise) with a `CircleMarker` per waypoint and a popup showing that waypoint's verdict/reasons, plus a "🔀 Rerouted around hazard" note with the original reasons when `rerouted` is set.
  - **Real shipping-lane routing:** `route_agent._compute_sea_route()` calls `searoute.searoute()` (offline, free, MIT-licensed, no API/key) between the two geocoded endpoints; when the network has resolution there (open-water port-to-port routes) it returns a real land-avoiding path, downsampled to at most `MAX_SEA_ROUTE_WAYPOINTS` (8) via `_sample_waypoints()` (always keeping the first/last point) before hazard-checking each one. searoute returns a degenerate single-point result for short/nearshore hops (e.g. within the same harbor or backwater), where the original direct-line linear-interpolation (`WAYPOINT_COUNT` = 5) remains the fallback. `route_source` ("shipping_lanes" or "direct_line_fallback") is returned in the output and disclosed in the trace's `sources` list.
- **Persistent per-session history:** `backend/app/db.py` is a small SQLite module (not the spec's literal "Postgres" — zero-config, file-based, no server process, gitignored at `backend/data/orca.db`) with `init_db()`, `get_history(session_id)`, `append_message(session_id, role, content)`. `POST /chat` doesn't trust client-sent history — it loads history from the DB by `session_id` and persists both the user's message and the final answer after each turn. `GET /sessions/{session_id}/history` lets the frontend restore history on page load.
- **Proactive hazard alerting**, delivered two ways:
  1. In-app, over a long-lived SSE endpoint (`GET /sessions/{session_id}/alerts/stream`), while a browser tab is open. `backend/app/alerting.py`: every 5 minutes (`DEFAULT_CHECK_INTERVAL_SECONDS`), every session with a known last-resolved location (`db.set_last_location`, captured automatically from the geospatial trace entry after each `/chat` turn) is re-checked against live `weather_agent`/`risk_agent` — the same agents the main pipeline uses, no new hazard logic (keys off the legacy `verdict` field, see the dual-risk-output note above). An alert publishes only on a **transition into "unsafe"** (`db.get_last_verdict`/`db.set_last_verdict` track state to avoid re-alerting every poll while still unsafe, or alerting on recovery to safe). Backed by an in-memory `dict[session_id, list[asyncio.Queue]]` subscriber registry (`subscribe`/`unsubscribe`/`publish`) — a 15s keep-alive `: ping` comment prevents proxy/load-balancer idle timeouts. The background poller starts via a FastAPI `lifespan` context manager (`asyncio.create_task(alerting.run_periodic_checks())`). Frontend: `chatClient.subscribeToAlerts()` wraps the native `EventSource` API (this endpoint is GET-only, unlike `/chat`, so `EventSource` works natively) and `page.tsx` shows a dismissible banner on the incoming alert. Real limitation: if no tab is open for a session, the alert is silently missed over this channel — which is what Web Push (below) closes.
  2. **Real Web Push**, reaching a session even with no tab open: the W3C Push API delivers directly through the browser vendor's own push service (Chrome → Google, Firefox → Mozilla), authenticated with VAPID keys generated and held locally — no third-party push service. `backend/app/push.py`: `get_vapid_public_key_b64()` generates/persists a VAPID keypair (`py_vapid`, file at `backend/data/vapid_private_key.pem`, gitignored) and `send_push(subscription_info, payload)` sends one notification (`pywebpush`). Table `db.push_subscriptions` (`save_push_subscription`/`get_push_subscriptions`, deduped by endpoint). Endpoints: `GET /push/vapid-public-key` (public), `POST /push/subscribe` (auth-required, session-ownership-checked). `alerting.check_hazards_once()` calls `_send_web_push()` alongside the SSE `publish()` on every unsafe-transition alert — same trigger, two delivery channels. Frontend: `frontend/public/sw.js` is the service worker (handles `push` and `notificationclick` only — no offline app caching); `frontend/lib/push.ts` (`isPushSupported`, `subscribeToPush`) registers it, requests `Notification.requestPermission()`, subscribes via `PushManager`, and posts the subscription to the backend; `page.tsx` has an "Enable hazard push notifications" button (hidden when unsupported). Real limitation: push delivery is best-effort (no guarantee with any push system) and requires HTTPS or localhost, so this only works as-is for local dev or a future HTTPS deployment.
- **Known LLM quirk, guarded against:** the planner occasionally emits a non-`null` placeholder instead of JSON `null` for an unset `place_name`/`start_place_name`/`end_place_name` — observed live as the literal string `"null"`/`""` (via the Ollama Cloud fallback path, which doesn't reliably honor JSON schema constraints) and separately as a bare `","` (via Omniroute's own routed models). A plain truthiness check treats any of these non-empty strings as a real place, which previously sent a no-location query down the route path with a nonsense geocoded location, or a single-location query down the two-point route branch (skipping weather/risk/ocean_analytics entirely). `graph.py`'s `_is_real_place()` guards every place-name check (`_route_after_planner`, `reporting_node`'s no-location fallback) — it requires the cleaned string to contain at least one alphanumeric character, not just be non-empty and not literally "null"/"none", so punctuation-only junk like `","` is rejected too. **If you see a new placeholder variant slip through, extend this function, don't special-case the caller.**
- **Real accounts/auth** (user-confirmed scope: email + password only, no OAuth, no email verification, no password reset). `backend/app/auth.py`: `hash_password`/`verify_password` (stdlib `hashlib.pbkdf2_hmac`, no new crypto dependency), `create_token`/`decode_token` (JWT via `pyjwt`, `JWT_SECRET` env var — falls back to an insecure fixed dev default, fine for a demo, not for any real deployment). Table `users` (`db.create_user`, `db.get_user_by_email`); `sessions.user_id` ties every session to exactly one owner. `POST /auth/signup` and `POST /auth/login` return a token; every other endpoint requires one — `Authorization: Bearer <token>` for `/chat` and `GET /sessions/{id}/history`, a `?token=` query param for `GET /sessions/{id}/alerts/stream` (native `EventSource` can't set headers). `db.ensure_session(session_id, user_id)` creates a session on first use or raises `SessionOwnershipError` (→ HTTP 403) if that `session_id` already belongs to someone else. Frontend: `AuthGate.tsx` gates the whole app behind login/signup; `page.tsx` stores the token in `localStorage` and scopes the session-id-per-browser key by email (`orca-session-id:<email>`).
- **Browser voice input/output** (user-confirmed scope: browser-based only — real SMS/phone/IVR isn't free at any real scale). `frontend/lib/voice.ts` wraps the Web Speech API (`SpeechRecognition`/`webkitSpeechRecognition` for input, `speechSynthesis`/`SpeechSynthesisUtterance` for output) behind `globalThis` rather than `window` — this project's test environment has no `window` at all (no jsdom), so this keeps the module genuinely unit-testable without adding a DOM test dependency. `ChatPanel.tsx` adds a mic button (feature-detected, hidden entirely in unsupported browsers) that transcribes one utterance into the input box, and a "read answers aloud" toggle. No backend involvement at all. Regional-language responses ride on the same `response_language` mechanism the planner already extracts (see below) and have been verified live end-to-end with a Hindi query producing a fully Hindi answer — not just a plumbing guess.
- **Language detection and response:** the planner's structured output includes `response_language` — the LLM identifies the language of the user's message and `reporting_agent.py`'s prompt instructs it to respond in that same language. There's no hardcoded language list or translation layer; this rides entirely on the LLM's own multilingual ability, and its reliability scales with whichever provider/model actually serves a given request (see LLM constraint below).
- **"Why has productivity changed" diagnostic**, using real data, not fabricated catch statistics (no free fisheries/catch dataset exists). `ocean_analytics_agent._productivity_trend()` compares whether SST was inside the favorable PFZ band (`SST_MIN_C`-`SST_MAX_C`) at the start vs. the end of the already-fetched 7-day SST trend, returning `"improving"`/`"declining"`/`"stable"`/`"unknown"` plus a real, data-cited `productivity_note`. This only covers the SST half of the PFZ score — there's no chlorophyll trend endpoint (only a point-in-time value), so a chlorophyll-driven productivity change wouldn't be reflected.
- **Real INCOIS Potential Fishing Zone (PFZ) advisory** (`connectors/pfz.py`, distinct from `connectors/incois.py`'s marine-forecast module described in the fabrication incident above) — the SST/chlorophyll-threshold `pfz_likelihood` heuristic stays as an independent signal, not replaced. `https://incois.gov.in/MarineFisheries/TextData` is a plain server-rendered HTML page (not a documented API), found by inspecting what a real INCOIS page serves (via a live `claude-in-chrome` session watching the "Select Sector" dropdown's navigation) rather than assuming nothing exists. It lists, per named coastal landing center, the bearing/distance/depth offshore to that center's current PFZ advisory point. Free, no key, no IP whitelist — unlike `api.imd.gov.in`, which does now exist (28 documented JSON endpoints including cyclone track/wind/cone-of-uncertainty) but requires manually-approved IP whitelisting; **IMD access stays unimplemented for that reason**, not for lack of a feed. The INCOIS page needs a Java servlet session: `_fetch_pfz_live()` hits `TextDataHome` once to acquire a `JSESSIONID` cookie, then requests `TextData?secid=<SEC00N>` with it. INCOIS splits the coast into 14 sectors chosen from a dropdown, not by lat/lon; `_resolve_sector()` reverse-geocodes the query point to an Indian state via Nominatim and maps state name to sector id. Tamil Nadu, Andhra Pradesh, and Andaman & Nicobar are each split into two INCOIS sectors with no Nominatim-reportable boundary between them; `SPLIT_STATE_SECTORS` approximates the split with a latitude threshold — a real simplification, not exact administrative geography. `_parse_landing_centers()` regex-parses the response's HTML table (plain stdlib `re`, no HTML-parsing dependency) and converts DMS lat/lon to decimal degrees; the nearest landing center's advisory point to the query location (haversine) is returned as `ocean_analytics_agent.py`'s `pfz_advisory` field. `reporting_agent.py`'s prompt leads "nearest fishing zone" answers with this real advisory when present, explicitly distinguished from the SST/chlorophyll `pfz_likelihood` heuristic.
- **IMD and ISRO/MOSDAC connectors are credential-gated and, as shipped, always cache-only.** `connectors/imd.py` (`get_imd_warnings`, warning level + coastal bulletin) and `connectors/mosdac.py` (`get_mosdac_satellite_data`, Oceansat-3 chlorophyll/turbidity/etc.) each check `settings.imd_api_key`/`settings.mosdac_token` and **raise immediately** if unset, which is the correct, honest pattern (contrast with the INCOIS incident above) — `fetch_with_fallback` then serves the committed snapshot, correctly marked `is_cached: True`. No `IMD_API_KEY`/`MOSDAC_TOKEN` is configured anywhere (neither is in `backend/.env`, even though other keys now are — see the Stormglass bullet below), and IMD's requires manual government IP-whitelist approval to obtain at all, so in practice every IMD/MOSDAC-sourced field is currently the same fixed Mangalore-area snapshot regardless of query location — real limitation, honestly disclosed via `is_cached`, easy to miss if you're not reading the trace. `weather_agent.py`'s IMD enrichment and `ocean_analytics_agent.py`'s MOSDAC enrichment now run concurrently with their sibling connector calls (`asyncio.gather` + a `_safe()` wrapper in each agent) rather than sequentially, since none of these calls depend on each other's results — this was a real latency fix, cutting one full connector round-trip's worth of sequential wait per agent.
- **Stormglass connector** (`connectors/stormglass.py`, `GET api.stormglass.io/v2/weather/point`) — real marine weather (wave height, swell height, wave period, surface current speed, water temperature), gated behind `STORMGLASS_API_KEY` (present in `backend/.env`, not committed). Response shape verified against a real authenticated call before writing any parsing code (the INCOIS incident's lesson applied directly): every requested parameter comes back nested by forecast-model source, e.g. `{"waveHeight": {"sg": 0.64, "noaa": 0.73, ...}}`, not a plain number — `_pick_source_value()` prefers `"sg"` (Stormglass's own blended model), falling back to whichever source is present. **The free tier is severely limited: verified live at `meta.dailyQuota: 10` requests/day for the whole app, not per-user.** No special rate-limiting/throttling code was added for this — a quota-exhausted response is just another live-fetch failure to `fetch_with_fallback`, which already falls back to the disclosed cached snapshot (a real captured example, not fabricated) exactly like IMD/MOSDAC without a key. In practice this means roughly the first ~10 chat queries each day get real Stormglass numbers; the rest honestly degrade to cache. Wired into `weather_agent.py` as a third concurrent enrichment call (alongside INCOIS and IMD) and applied *last*, so its real numbers take final precedence over INCOIS's always-cached values when live. `backend/.env` also carries keys for OpenWeatherMap/Tomorrow.io/Weatherstack/OpenCage/Mapbox/Positionstack (see `.env.example`) that are **not** wired into any connector yet — `config.py`'s `Settings` uses `extra="ignore"` specifically so unused keys in `.env` don't break `Settings()` for everyone.
- **Evidence-grounded reasoning and verification.** Every `MarineParameter` a connector emits (weather, tide, ocean analytics) accumulates in `GraphState["evidence"]` across the pipeline, not just the final headline numbers. `verification_agent.audit_marine_evidence()` runs in `reporting_node` before answer synthesis, checking source provenance against a known-provider allowlist and evidence presence/freshness, and returns a `VerificationResult` (`is_verified`, `data_status`, `checks_passed`, `issues`, `confidence`) that's returned alongside the answer and rendered by `EvidencePanel.tsx` (a collapsible accordion of every cited observation, its source, and its `data_status`) and surfaced in `RecommendationHero.tsx`'s headline card — so a thin/stale/unverifiable answer looks visibly different from a well-grounded one, not just different in prose.
- **What-if comparisons.** `what_if_agent.run_what_if_agent()` re-runs `risk_engine.calculate_risk()` for an alternative departure time and/or a spatial relocation (`calculate_destination_coords()` — cardinal directions or "offshore"/"seaward", which resolves toward open water via `geospatial.compute_coastal_distance()`'s `coast_side`), producing a `WhatIfComparison` (original vs. alternative risk score/level, a per-parameter `differences` breakdown, and a verdict). Triggered from `reporting_node` when the plan or message text implies a what-if ("what if", "instead", a move-distance/direction). Rendered by `frontend/components/WhatIfCard.tsx`.

**LLM constraint:** a two-provider fallback chain implemented in `app/llm.py`'s `LLMClient` — no paid-per-token API of any kind for either provider. Priority provider is **Omniroute**, a local OpenAI-compatible proxy at `http://127.0.0.1:20128/v1` (`OMNIROUTE_API_KEY`); it reliably enforces JSON-schema-constrained structured output (`response_format: json_schema`), which the planner depends on. Fallback provider is **Ollama Cloud** (`https://ollama.com/api`, `OLLAMA_API_KEY`, model `gemma4:31b`) for when Omniroute is unreachable — Ollama Cloud does *not* reliably honor schema constraints, so its path does manual JSON extraction from the response text with one retry before giving up. `LLMClient` exposes `generate_text(system_prompt, user_message)` and `generate_structured(system_prompt, user_message, schema)`; agents never talk to a provider SDK directly. Both agents that call an LLM (`planner.py`, `reporting_agent.py`) go through this client.

*Portability caveat:* Omniroute only exists on the machine it was configured on (`127.0.0.1`) — the app will only reach it when run from that same machine with the proxy already running. Anywhere else (a fresh clone, a deploy target, a different developer's machine), only the Ollama Cloud fallback path is reachable. (History: the original Phase 1 implementation used Google Gemini's free tier, which broke when `gemini-2.5-flash` was deprecated for new API keys and its successors proved unreliable/rate-limited on a fresh key; switched to the current two-provider chain.)

**Other deliberate deviations from a naive reading of the spec:** SST/chlorophyll come from NOAA ERDDAP (`jplMURSST41`, `erdMH1chla1day` — free, no registration) rather than Copernicus/NASA (note: `erdMH1chla1day` has been frozen upstream since 2022-07-25 — chlorophyll data is real but stale; SST from the same query is live); the map uses Leaflet + OpenStreetMap tiles (no API key) rather than Mapbox.

**Frontend (`frontend/`):** the backend's `/chat` endpoint streams Server-Sent Events (`event: trace`, `event: answer`) over a POST request — the native `EventSource` API doesn't support POST, so the client (`frontend/lib/chatClient.ts`) hand-parses the stream via `fetch` + `ReadableStream`. `MapView` (Leaflet) must be loaded via `next/dynamic` with `ssr: false` since Leaflet touches `window`. `ChatPanel.tsx` composes `RecommendationHero.tsx` (headline verdict/risk/verification card, with a loading skeleton state), `WhatIfCard.tsx` (conditional), the synthesized answer text, and a collapsible `EvidencePanel.tsx` per assistant message — see `docs/frontend-features.md` for the full feature-to-contract mapping.

## Commands

Backend (from `backend/`, inside the `venv`/`.venv` virtualenv):
- `pytest -v` — run all tests
- `pytest tests/test_route_agent.py -v` — run a single test file
- `pytest tests/test_route_agent.py::test_run_route_agent_all_safe_waypoints -v` — run a single test
- `uvicorn app.main:app --reload --port 8000` — run the dev server (needs `OMNIROUTE_API_KEY` and/or `OLLAMA_API_KEY` env vars — see [LLM setup in README.md](./README.md#llm-setup); Omniroute only works when its local proxy is running on the same machine; set `JWT_SECRET` for anything beyond a local demo — see `app/config.py`)
- No backend linter/formatter is configured in this repo — don't invent a lint command.

Frontend (from `frontend/`):
- `npm test` — run all Vitest unit tests (equivalent to `vitest run`)
- `npx vitest run lib/push.test.ts` — run a single test file
- `npx vitest run -t "throws when push is unsupported"` — run a single test by name
- `npx tsc --noEmit` — type-check
- `npm run lint` — ESLint
- `npm run dev` — run the dev server (expects backend at `http://localhost:8000`, override via `NEXT_PUBLIC_BACKEND_URL`)
